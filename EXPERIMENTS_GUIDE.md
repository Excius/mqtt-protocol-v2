# MQTT-NG Experiments Guide

This guide explains every script in the project, what it does, what it produces,
and exactly how to run it — from first clone to final graphs.

---

## Quick Start (Run Everything)

```bash
# 1. Install Python dependencies (plotting only)
pip install pandas matplotlib numpy

# 2. Build all client binaries
go build -o load ./client/load
go build -o probe ./client/probe
go build -o publisher ./client/publisher
go build -o subscriber ./client/subscriber
go build -o priority_bench ./client/priority_bench
go build -o auth_injector ./client/auth_injector
go build -o property_injector ./client/property_injector

# 3. Build broker binary
cd broker && go build -o ../broker_bin ./cmd && cd ..

# 4. Run every experiment in sequence (~15-20 minutes total)
bash experiments/run_all.sh

# 5. Generate all 11 summary graphs
python3 experiments/generate_summary_graphs.py
# Graphs saved to: docs/graphs/
```

## Prerequisites

| Tool | Required For | Check |
|---|---|---|
| Go 1.21+ | Building broker and all clients | `go version` |
| Python 3.9+ | Plotting scripts | `python3 --version` |
| `pandas`, `matplotlib`, `numpy` | All Python plot scripts | `pip install pandas matplotlib numpy` |
| `openssl` | TLS cert generation + TLS profile experiment | `openssl version` |
| Linux kernel 5.6+ | eBPF/XDP module | `uname -r` |
| Root or `CAP_BPF` | Kernel-level XDP attach (eBPF module) | optional — module falls back gracefully |

**Python venv (used by all scripts):**
```bash
python3 -m venv ~/.venv
~/.venv/bin/pip install pandas matplotlib numpy
```
All experiment scripts call `$HOME/.venv/bin/python` — the venv is automatically used.

## Environment Variables (Control Speed & Scale)

All `run_present_state_capture.sh`-based scripts honor these variables to control experiment duration:

```bash
# Default values shown — reduce for faster runs, increase for more accurate results
export EQUAL_TIER_DURATION_S=10     # seconds per load tier (normal / high / very_high)
export IDLE_DURATION_S=5            # seconds for idle resource baseline measurement
export CONNECT_ATTEMPTS=80          # number of connection latency samples
export RECONNECT_ATTEMPTS=50        # number of reconnect latency samples
export PUBSUB_QOS0_SAMPLES=120      # number of pub/sub QoS0 RTT samples
export PUBSUB_QOS1_SAMPLES=120      # number of pub/sub QoS1 RTT samples
```

**Fast run (for quick iteration):**
```bash
export EQUAL_TIER_DURATION_S=5 IDLE_DURATION_S=3 CONNECT_ATTEMPTS=30 RECONNECT_ATTEMPTS=20 PUBSUB_QOS0_SAMPLES=50 PUBSUB_QOS1_SAMPLES=50
```

## Experiment-by-Experiment Reference

---

### `experiments/run_all.sh` — Master Runner

**What it does:** Runs all 12 experiments in a sensible order (baseline first, then per-module, then combined). Writes a `results/FULL_RUN_SUMMARY.txt` with PASS/FAIL/duration for each.

```bash
bash experiments/run_all.sh
```

**Output:** `results/FULL_RUN_SUMMARY.txt`

---

### `experiments/baseline/run_baseline_only.sh` — Pure Baseline Reference

**What it does:** Starts the broker with `--modules=baseline` (zero extra modules). Measures idle resource usage, load throughput at 3 concurrency tiers (20/60/120 workers), and latency distributions (connect, reconnect, pub/sub QoS0+1). This is the canonical zero-overhead reference point every other module should be compared against.

```bash
bash experiments/baseline/run_baseline_only.sh
```

**Output:** `results/baseline_mqttv5/`
- `load/summary.csv` — throughput + CPU/memory per tier
- `latency/latency_summary.csv` — p50/p95/p99 latency for all probe modes
- `latency/plots/` — latency CDF, histogram, percentile charts
- `load/plots/` — CPU/RSS trend during load

---

### `experiments/tls_resumption/run_tls_resumption_comparison.sh` — TLS Session Resumption

**What it does:** Runs two broker instances back-to-back — one with `baseline` (no resumption) and one with `tls-session-resumption`. Uses `probe reconnect` mode to measure first-connect vs. reconnect latency and compute the speedup. Also runs `openssl s_client` twice to confirm `tls_second_reused` is `false` (no resumption) vs. `true` (with resumption).

**Module tested:** `tls-session-resumption`  
**Expected result:** ~2× faster reconnect when the module is on.

```bash
bash experiments/tls_resumption/run_tls_resumption_comparison.sh
```

**Output:** `results/tls_resumption/`
- `summary.csv` — per-scenario: speedup_x, avg connect/reconnect ms, tls_second_reused
- `raw/old_no_resumption/` + `raw/new_with_resumption/` — raw CSVs + broker logs
- `plots/` — speedup bar chart

---

### `experiments/tls_profiles/run_tls_profiles_comparison.sh` — Adaptive TLS Profiles

**What it does:** Runs three broker instances on different ports — `LOW_POWER`, `BALANCED`, `HIGH_SECURITY`. Each gets the same load and latency probes. Uses `openssl s_client` to verify the actually negotiated TLS version, cipher, and curve for each profile.

**Module tested:** `adaptive-tls-profiles`  
**Expected result:** LOW_POWER negotiates TLS 1.2 + ChaCha20 + X25519; HIGH_SECURITY negotiates TLS 1.3 + P384.

```bash
bash experiments/tls_profiles/run_tls_profiles_comparison.sh
```

**Output:** `results/tls_profiles/`
- Per-profile subdirectories with full load + latency data
- `plots/` — handshake latency comparison across profiles

---

### `experiments/property_validator/run_property_validator_comparison.sh` — Property Validator Defense

**What it does:** Runs two scenarios — `baseline` (no defense) then `property-validator`. In each, starts the broker, then launches `client/property_injector` as the attacker (sends MQTT PUBLISH packets with 50 oversized user properties at high concurrency for 10 seconds). Records peak broker memory and throughput.

**Module tested:** `property-validator`  
**Expected result:** Broker peak memory drops from ~6 GB to ~25 MB under the attack.

```bash
bash experiments/property_validator/run_property_validator_comparison.sh
```

**Output:** `results/property_validator/`
- `summary.csv` — scenario, peak CPU %, peak memory MiB, total_sent, total_errors
- `raw/` — broker logs for each scenario

---

### `experiments/auth_defense/run_auth_flood_comparison.sh` — Auth Flood Defense

**What it does:** Runs two scenarios — `baseline` then `auth-defense`. In each, starts the broker, then launches `client/auth_injector` in `flood` mode (50 concurrent attackers for 10 seconds, each sending rapid AUTH packets). Records total AUTH packets accepted and broker CPU.

**Module tested:** `auth-defense`  
**Expected result:** AUTH packets received drops from ~90,000 to ~2,000.

```bash
bash experiments/auth_defense/run_auth_flood_comparison.sh
```

**Output:** `results/auth_defense/`
- `summary.csv` — scenario, modules, CPU %, memory MiB, total_connects, total_sent, total_errors

---

### `experiments/message_integrity/run_experiment.sh` — Message Integrity (HMAC)

**What it does:** Runs a baseline capture, then a `message-integrity` capture. The load generator signs every PUBLISH with HMAC-SHA256 (via `MQTT_INTEGRITY_SECRET=default-broker-secret`). The broker verifies every signature. Measures CPU overhead of the cryptographic verification under load.

**Module tested:** `message-integrity`  
**Expected result:** Zero publish errors; modest CPU increase (~4-7% at very high load).

```bash
bash experiments/message_integrity/run_experiment.sh
```

**Output:** `results/message_integrity/`
- `baseline/` and `module/` — full load + latency capture for each
- `comparison_plots/` — CPU comparison chart

---

### `experiments/priority_messaging/run_experiment.sh` — Priority Messaging (Overhead)

**What it does:** Measures the overhead of the priority-messaging module under uniform `Urgent`-priority load. Compares baseline vs. module CPU, latency, and throughput.

**Module tested:** `priority-messaging`  
**Expected result:** Negligible latency/throughput difference; small CPU overhead from scheduler goroutines.

```bash
bash experiments/priority_messaging/run_experiment.sh
```

**Output:** `results/priority_messaging/`

---

### `experiments/priority_messaging/run_ordering_experiment.sh` — Priority Ordering (Real Reordering Evidence)

**What it does:** Sends a flood of Normal-priority messages from many concurrent clients, with one Urgent message interleaved mid-flood on one of those connections. Measures the Urgent message's receive rank as a fraction of the flood. Runs N trials for statistical confidence.

**Module tested:** `priority-messaging` (ordering benefit, not just overhead)  
**Expected result:** With the module, Urgent messages arrive earlier than chance (lower rank percentage) compared to baseline.

```bash
bash experiments/priority_messaging/run_ordering_experiment.sh
```

**Output:** `results/priority_messaging_ordering/`
- `ordering_results.csv` — per-trial: urgent_rank_pct for baseline and module scenarios

---

### `experiments/wildcard_tokens/run_experiment.sh` — Wildcard Capability Tokens

**What it does:** Starts the broker with `wildcard-tokens`, then runs a background `subscriber` client that connects, receives its wildcard token in the CONNACK, and subscribes to `#`. Measures CPU overhead of having an active wildcard ACL subscriber during load.

**Module tested:** `wildcard-tokens`  
**Expected result:** Slight CPU increase due to fan-out to the wildcard subscriber; ACL checks for exact-topic publishes are trivial.

```bash
bash experiments/wildcard_tokens/run_experiment.sh
```

**Output:** `results/wildcard_tokens/`

---

### `experiments/quic_transport/run_experiment.sh` — QUIC Transport

**What it does:** Runs two captures — one with the broker over TCP+TLS (`baseline`), one with the broker over QUIC (`quic-transport`). The load generator and probe use `quic://` URLs. Compares connect/reconnect/pub-sub latency and throughput between the two transports.

**Module tested:** `quic-transport`  
**Expected result:** 100% probe success over QUIC; QUIC handshake is slightly slower than warm TCP+TLS on loopback; steady-state pub/sub latency is comparable.

> **Requirement:** TLS certs must exist. They are auto-generated by the script if missing.

```bash
bash experiments/quic_transport/run_experiment.sh
```

**Output:** `results/quic_transport/`
- `baseline/` and `module/` — full load + latency data
- `comparison_plots/` — latency comparison chart

---

### `experiments/ebpf_filter/run_experiment.sh` — eBPF Kernel Filter

**What it does:** Runs two captures — a clean `baseline`, then `ebpf-filter`. With the module active, the broker bans the load generator's IP after it exceeds 10 connections/second. High/Very-high load tiers show 100% connection failure (successful ban).

**Module tested:** `ebpf-filter`  
**Expected result:** Normal tier: partial success (ban triggers mid-tier). High + Very-high: 100% connect errors.

> **Note on privileges:** Without `CAP_BPF` / root, the XDP kernel attachment fails gracefully — the broker continues with application-layer rate limiting only. The self-ban behavior is still demonstrated at the Go hook level.

```bash
# As root for full XDP kernel-level blocking:
sudo bash experiments/ebpf_filter/run_experiment.sh

# Without root (application-layer fallback still bans):
bash experiments/ebpf_filter/run_experiment.sh
```

**Output:** `results/ebpf_filter/`

## Client Tool Reference

These are the Go programs in `client/` used by the experiment scripts. You can also run them manually.

### `client/load` — Load Generator

```bash
# Usage: load <workers> [messages_per_worker] [delay_ms] [reconnect_every]
./load 20 400 20 0   # 20 workers, 400 msgs each, 20ms delay, no periodic reconnect

# Key environment variables:
export MQTT_BROKER_URL=tcp://localhost:1883    # or tls://, quic://
export MQTT_INTEGRITY_SECRET=default-broker-secret   # enables HMAC signing
export MQTT_PRIORITY=Urgent                    # sets priority user property
export MQTT_TLS_INSECURE_SKIP_VERIFY=true      # skip TLS cert validation
export MQTT_TLS_CA_FILE=/path/to/ca.cert.pem   # trust this CA
```

### `client/probe` — Latency Probe

```bash
# Connect latency
./probe connect --broker tcp://localhost:1883 --attempts 80 --out connect_latency.csv

# Reconnect + session-resumption speedup
./probe reconnect --broker ssl://localhost:8883 --attempts 50 --out reconnect_latency.csv

# Pub/sub round-trip RTT
./probe pubsub --broker tcp://localhost:1883 --samples 120 --qos 0 --out pubsub_rtt.csv
```

### `client/subscriber` — Subscriber (Wildcard Token Aware)

```bash
export MQTT_BROKER_URL=tcp://localhost:1883
export MQTT_TOPIC="sensors/+/temp"    # supports wildcards (requires token)
./subscriber
```

### `client/auth_injector` — Auth Flood Attacker

```bash
./auth_injector --broker localhost:1883 --concurrency 50 --duration 10s --type flood
./auth_injector --broker localhost:1883 --concurrency 50 --duration 10s --type slowloris
```

### `client/property_injector` — Property Flood Attacker

```bash
./property_injector --broker localhost:1883 --concurrency 10 --duration 10 \
    --prop-count 50 --key-size 100 --val-size 100
```

### `client/priority_bench` — Priority Ordering Benchmark

```bash
./priority_bench --broker tcp://localhost:1883 --flood-size 1000 \
    --concurrency 20 --trials 40 --out ordering_results.csv
```

## Running the Broker Manually

```bash
cd broker
go build -o ../broker_bin ./cmd

# Baseline (no modules):
../broker_bin --modules=baseline --tcp :1883 --ws :1882

# Multiple modules:
../broker_bin --modules=message-integrity,priority-messaging,wildcard-tokens --tcp :1883 --ws :1882

# With TLS:
../broker_bin --modules=tls-session-resumption,adaptive-tls-profiles \
    --tls-cert-file experiments/baseline/certs/server.cert.pem \
    --tls-key-file experiments/baseline/certs/server.key.pem \
    --tls-profile HIGH_SECURITY --tcp :8883

# With QUIC:
../broker_bin --modules=quic-transport \
    --tls-cert-file experiments/baseline/certs/server.cert.pem \
    --tls-key-file experiments/baseline/certs/server.key.pem \
    --quic :4433 --tcp :1883

# All supported modules:
# baseline, tls-session-resumption, adaptive-tls-profiles,
# property-validator, auth-defense, message-integrity,
# priority-messaging, wildcard-tokens, quic-transport, ebpf-filter
```

## Troubleshooting

| Problem | Likely Cause | Fix |
|---|---|---|
| `address already in use` | A previous broker didn't shut down | `pkill -f broker_bin` or `lsof -i :1883` |
| `tls: server did not select an ALPN protocol` | QUIC experiment: certs don't have `NextProtos` set | This was a fixed bug — ensure `broker/cmd/main.go` has `tlsConfig.NextProtos = []string{"mqtt"}` |
| `operation not permitted` in eBPF logs | Running without root/CAP_BPF | Expected — module falls back to app-layer rate limiting gracefully |
| `Missing or empty CSV` from plot script | Experiment didn't finish or produced 0 successful samples | The eBPF experiment's 0% success is correct behavior (self-ban) — plotting handles it gracefully |
| Property-validator + load client stalls | Per-client budget (32KB) exhausted by long-running workers | Each publish has a 2s timeout — should fail fast now; if stalling, check `client/load` publish timeout |
| QUIC `pubsub_qos1` shows negative avg_ms | Measurement precision artifact on loopback | Not a bug; the values are within noise of zero and don't represent real negative latency |
